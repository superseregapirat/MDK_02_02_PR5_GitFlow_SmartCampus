# 1. Модель ветвления и командные роли

Для координации распределенной разработки **АИС «Умный кампус»** применяется стратегия **Git Flow**. Такой подход необходим из-за наличия в системе нескольких независимых контуров (учебное расписание, контроль доступа через турникеты, мобильное приложение студента) и жесткой привязки релизов к учебному календарю вуза.

В репозитории поддерживаются две долгоживущие ветки (`main` — боевой контур на серверах университета; `develop` — стенд для интеграционного тестирования новых модулей) и три типа вспомогательных веток (`feature/*`, `release/*`, `hotfix/*`).

### Распределение зон ответственности в команде

* **Tech Lead (Тимлид):** контролирует соблюдение модульной архитектуры .NET-решения, администрирует правила защиты веток (`Branch Protection`), проводит итоговую проверку Pull Request перед слиянием в `develop`, формирует релизные ветки к началу семестра и координирует экстренные патчи.
* **Backend Developer (.NET/C#):** проектирует и реализует серверную логику (алгоритмы проверки накладок в расписании, генерацию криптографических токенов пропусков, шлюзы обмена данными с контроллерами СКУД), пишет модульные тесты.
* **Mobile / Frontend Developer:** разрабатывает интерфейс личного кабинета студента и преподавателя, реализует экран отображения актуального расписания и модуль генерации динамического QR-кода / NFC-метки для прохода через турникеты.
* **QA Engineer (Инженер по тестированию):** проводит регрессионное тестирование в ветках `release/*`, проверяет корректность работы пропусков на тестовом стенде СКУД и валидирует граничные случаи в расписании.

# 2. Жизненный цикл фичи (Feature Branch Lifecycle)

Процесс разработки новой функциональности регламентирован на примере задачи **«Реализация временного гостевого пропуска для участников университетской конференции»**:

1. **Инициализация ветки задачи:**
   Разработчик обновляет локальную ветку `develop` и создает от нее новую рабочую ветку с префиксом `feature/` и номером тикета из Jira/YouTrack:
   ```bash
   git checkout develop && git pull origin develop
   git checkout -b feature/CAMPUS-408-guest-pass
   ```

2. **Итеративная разработка и фиксация изменений:**
   Реализация разделяется на небольшие логические шаги. Коммиты оформляются по спецификации *Conventional Commits* с указанием модуля в скобках:
   ```bash
   git commit -m "feat(passes): implement time-limited QR payload generator"
   git commit -m "test(passes): add expiration boundary unit tests"
   ```

3. **Публикация ветки и синхронизация:**
   По завершении разработки программист подтягивает актуальные изменения из `develop` (через `git rebase develop`) для предотвращения конфликтов слияния и отправляет ветку в удаленный репозиторий:
   ```bash
   git push -u origin feature/CAMPUS-408-guest-pass
   ```

4. **Создание Pull Request (PR):**
   В GitLab/GitHub открывается запрос на слияние `feature/CAMPUS-408-guest-pass -> develop`. В шаблоне PR заполняются: описание бизнес-логики, примеры JSON-запросов для нового эндпоинта, скриншоты из Swagger и отметка о прохождении локальных тестов.

5. **Автоматический конвейер проверок (CI):**
   При открытии PR автоматически запускается пайплайн: компиляция решения (`dotnet build`), запуск всех тестов (`dotnet test`), проверка форматирования (`dotnet format --verify-no-changes`) и сканирование зависимостей на уязвимости. При падении любого этапа кнопка слияния блокируется.

6. **Ревью кода и интеграция:**
   После получения одобрения от команды и Tech Lead выполняется слияние методом **Squash and Merge** (объединение всех рабочих коммитов фичи в один чистый коммит в истории `develop`), после чего временная ветка `feature/CAMPUS-408-guest-pass` автоматически удаляется.
